4.1 Why mtime and Remote Build Farms Are Band-Aids

Classical build systems — from 1976 make to modern Ninja + Goma/RBE — still answer the wrong question: "Is file A.cc newer on disk than A.obj?"

Timestamp-driven builds fail in three catastrophic ways:

  • False Invalidation: Switching git branches, touching a comment, or editing a single function in a 3,000-line .cc file forces the entire translation unit to recompile.
  • Header Cascade: Editing one unrelated declaration in a shared header invalidates every TU that transitively includes it.
  • Cloud Latency Tax: Instead of fixing the granularity of compilation, Von Neumann teams ship gigabytes of preprocessed .cc files to remote RBE clusters — paying network RTT, serialization overhead, and cloud bills just to run clang elsewhere.

The White Dragon Principle: Never ask when a file changed. Ask what cryptographic hash each semantic block and transitive header closure has — and store the compiled artifacts in a local, zero-copy .b8p (0x50473842 'B8GP') WASM Trie CAS pack.

4.2 Anatomy of a .b8p CAS Object Pack

@awesome-os/b8g-cxx replaces loose .obj directory trees with target-bucketed .b8g-cas/*.b8p packs containing a /.b8oc-index.json manifest and /cas/<sha256>.obj payloads. Every lookup is computed from three deterministic layers:

  • Deduplicated HeaderDigestSlab: Parses #include closures in RAM once per build wave, hashing each header's normalized content exactly once instead of per-TU.
  • Shared Transitive PCH (/Yc + /Yu /Fp): Automatically synthesizes a content-keyed precompiled header for the common include preamble across a target bucket.
  • Sub-TU Code-Block Chunking (cc-block-chunker.mts): Splits a C++ .cc file into top-level function/class blocks, hashes each block independently, compiles only the mutated block against the cached PCH, and merges cached + fresh block .objs via lld-link /lib.
// packages/@awesome-os/b8g-cxx — Sub-TU Content-Addressed Block Pipeline
import { splitCxxSourceIntoBlocks, compileCxxUnitByBlocks } from '@awesome-os/b8g-cxx/blocks'
import { B8pObjCache, HeaderDigestSlab } from '@awesome-os/b8g-cxx/cas'

const slab  = new HeaderDigestSlab()
const cache = await B8pObjCache.open('.b8g-cas/v8-cctest.b8p')

// 1. Split translation unit into independently hashable top-level code blocks
const blocks = splitCxxSourceIntoBlocks(sourceText)

// 2. Hash (compilerFlags + pchDigest + blockNormalizedText) -> SHA-256 CAS key
//    On a 3-block .cc with 1 edited function: 2 CAS hits, 1 block compiled (< 190 ms)
const result = await compileCxxUnitByBlocks({
  unitPath: 'src/objects/js-array.cc',
  blocks,
  headerSlab: slab,
  casPack: cache,
  reuseSharedPch: true,
})

4.3 Interface Stubs (!ifs-v1 / .api.digest) & 8.04 ms DEPS Resolution

Content-addressed caching only reaches full leverage when downstream link steps stop invalidating on private implementation edits. @awesome-os/b8g-cxx/stubs emits four deterministic artifacts from a shared library's public C-ABI surface:

  • v8.ifs (!ifs-v1 textual ELF/COFF interface stub) and v8.def (30 exported symbols including b8g_v8_fastcall_no_receiver).
  • v8.api.digest (SHA-256 of the exported ABI surface; if unchanged, downstream linkers skip relinking completely).
  • v8.stub.lib (COFF import library compiled directly from the stub, enabling 90.52 ms zero-v8.h consumer compiles).

The same content-addressed discipline applies to dependency graphs. Traditional gclient sync invokes Python subprocesses and network round-trips over Chromium's 4,968-line DEPS file. b8g-deps-engine.mts evaluates the entire DEPS graph deterministically in memory in 8.04 ms, resolving every pinned revision against local .b8p (0x50473842 'B8GP') CAS hashes with zero redundant I/O.
